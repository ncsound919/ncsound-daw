## 2. Release blockers

Severity: **P0** = cannot ship; **P1** = audible/data-loss/red-gate risk; **P2** = functional/quality; **P3** = cleanliness.

### A-01 — P0 — The release tree does not exist in source control

`git status`: 18 modified paths and **5 untracked paths**. Two of the untracked files are required to build:

- `app/Source/MixRackDsp.h` — included by `app/Source/MixRack.cpp:3`
- `ui/src/workspace/RackPanel.tsx` — imported by `ui/src/workspace/Workspace.tsx:22`

`ui/src/console-ui/panels/Studio.tsx` and `eqCurve.ts` are untracked dead code (see A-13); `docs/MIXRACK_V3.md` is referenced by `README.md`.

Consequences:

1. `git commit -a` produces a tree that **cannot compile** (missing header) and **cannot typecheck** (missing module).
2. CI runs on pushed commits. None of the MixRack v3 work, the new routes, the new 12 native tests or the UI faceplates exist in CI.
3. The audit ran against a tree that another session was editing and relinking; artifact mtime/size changed mid-run (app exe went from 2,097,152 B to 7,940,608 B).

**Fix:** freeze the tree, add all five files, commit, push, and verify a clean-clone build. Until then every other result is provisional.

### A-02 — P0 — `ctest` is red: three of the four new mock tests abort the binary

`ctest --test-dir build -C Release --output-on-failure` → **195/196, exit 8**. `mix_rack` exits `0xc0000409` after 500 s.

Reproduced directly:

```
NCMixRackTests.exe "[mock]"                                  -> -1073740791 (0xC0000409)
NCMixRackTests.exe "*captures hardware input*"               -> -1073740791
NCMixRackTests.exe "*multi-channel concurrent*"              -> -1073740791
NCMixRackTests.exe "*streaming thread*"                      -> -1073740791
NCMixRackTests.exe "*life cycle*"                            -> 0 (passes)
```

Windows Error Reporting: `BEX64`, faulting module `ucrtbase.dll`, `0xc0000409` sub-code 7 (`FAST_FAIL_FATAL_APP_EXIT`, i.e. `abort()`/`std::terminate`), **before any Catch2 result is written** (the JUnit file contains only the opening tag). The take test leaves `%TEMP%\nc-mock-interface-take-verification\Track 1 take 1.wav` of **104 bytes — a RIFF header plus a `JUNK` chunk and no audio**. The folder is not deleted because the process dies before the test's cleanup.

So the one test that exercises a real recorded take end-to-end neither reports a pass nor a readable failure, and the take file itself is empty. `docs/MIXRACK_V3.md` documents this as "can crash … on machines without a free audio device"; it also aborts on this machine, which has audio devices, and only the lifecycle test survives.

**Fix:** make the mock fixture hermetic (no dependence on a real default device; no assertion in the fixture constructor; explicit writer-thread join before the fixture dies), register it as `SKIP_RETURN_CODE` when no device exists, and make a take write non-zero frames. Then `ctest` must be green on a machine with the speakers disabled.

### A-03 — P0 — CI is red on two UI gates and the release workflow cannot package the app

Executed on the current tree:

```
node node_modules/eslint/bin/eslint.js .        -> exit 1, 5 errors / 69 warnings
node node_modules/prettier/bin/prettier.cjs --check . -> exit 1, 11 files
```

The five errors are `react-hooks/rules-of-hooks` in **`ui/src/console-ui/panels/Studio.tsx:85-89,191`** — hooks (`useBound`/`useSpec`) called conditionally:

```tsx
const gain = band.gainKey ? useBound(band.gainKey) : null;
```

`ci.yml` runs `npm run lint` and `npm run format:check` on every push. Both fail.

The release workflow has a second, independent defect: `.github/workflows/release.yml` builds **only** `NCChopStation NCEightOHeight`, then runs `cpack -G ZIP`. `app/CMakeLists.txt:328` installs `NCSoundHub` with `COMPONENT app`, so the install step needs `NCSound Hub.exe`; it was never built in that job. A release run will either fail or produce a ZIP without the application (the `verify-package.sh` check does not look for the app binary).

**Fix:** fix/delete the dead Studio code, run Prettier, and build `NCSoundHub` (or all targets) before CPack in the release job. Add app-exe, `LICENSE` and notices assertions to `verify-package.sh`.

### A-04 — P0 — The installer is stale, incomplete, unreproducible, and missing prerequisites

Evidence:

- `build/ncsound-daw-0.1.0-AMD64.exe` is **385,326 bytes**, older than its own generated script (`project.nsi`, 5:44 AM vs installer 5:21 AM).
- The generated `project.nsi` has sections for **`docs` and `plugins` only**. There is no `app` section and no `File` command for `NCSound Music Hub.exe`.
- The NSIS staging tree (`build/_CPack_Packages/win64/NSIS64/ncsound-daw-0.1.0-AMD64`) contains docs and the VST3/Standalone binaries but **no app executable**.
- `cpack -G NSIS64` now fails with **"Cannot find NSIS compiler makensis"** — the toolchain that produced the artifact is not installed or documented, so the installer cannot be reproduced on this machine.
- The app imports `MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll` (confirmed with `dumpbin /dependents`). The installer carries no VC++ redistributable and no WebView2 Evergreen bootstrapper; a clean Windows 10 VM will fail to launch or show a blank WebView.
- The installer places VST3 bundles in `$INSTDIR\VST3`, not in `$COMMONFILES64\VST3`; hosts will not find them. This contradicts Gate 3 in `docs/RELEASE-GATES.md`.
- The executable is **unsigned** (`Get-AuthenticodeSignature` → `NotSigned`), so SmartScreen warns on first run.

The ZIP (`build/pkg/ncsound-daw-0.1.0-AMD64.zip`) does contain the app, both VST3s, both standalone apps, `LICENSE`, notices and docs, and `tools/verify-package.sh` passes it — but that script checks only the VST3 bundles, not the app or the legal files.

**Fix:** build the app before CPack, install VST3s to `$COMMONFILES64\VST3`, bundle or detect the VC++ redist and WebView2 Runtime, sign the binaries, make `makensis` part of `tools/fetch-native-deps.ps1`, and extend `verify-package.sh` to assert the app, licence, notices and version. Then run Gate 3 on a clean VM.

## 3. High-severity findings

### A-06 — P1 — Mixology Autopilot is a developer-machine feature that freezes the UI

`app/Source/WebViewBridge.cpp:871-889` calls `runMixologyAutopilot` **synchronously on the message thread**. That function:

1. Renders the whole session (`engine.renderToWav`), then
2. spawns a Python child process and calls `process.readAllProcessOutput()` with **no timeout** (`app/Source/MixologyBridge.cpp:220-229`), then
3. optionally renders and measures a second pass, then
4. applies ~hundreds of parameters.

The WebView cannot repaint "Analysing…" until the call returns; a hung child blocks the app indefinitely. The Earshot home defaults to **`D:/assets/earshot-main`** (`MixologyBridge.cpp:183-186`), a path that exists only on this development machine, and the measurement script is built with `sys.path.insert` on that folder. The two temporary WAVs are fixed names in `%TEMP%` (`nc-mixology-autopilot.wav`, `-pass2.wav`) and are never deleted.

A shipped user without Earshot sees "EARSHOT FAILED"; with a hung process they see a frozen window; two app instances collide on the temp file.

**Fix:** run it on a worker with progress/cancel, add a child-process timeout and kill, use a unique temp directory and delete it, and make the Earshot location a supported setting with a packaged default (or hide Autopilot unless it is configured). Until then it is a lab feature, not a shipped one.

### A-07 — P1 — The streaming-cache refill race is still open

`docs/engine-components-audit.md` ranks this first: "the only race found that a normal user can hear". The code is unchanged in the substantive respect:

`app/Source/AssetLibrary.cpp:145-169` — `serviceStreaming` fills slot `1 - active`, then publishes `slotStart`, `slotLength` and `activeCache`. A slot has **no publish stamp**. Two refills in quick succession (e.g. a seek or a large position jump) can target a slot a late block still reads, producing a torn sample/click. There is still no test that plays a streamed asset across a refill.

**Fix:** stamp each slot with the transport block counter and refuse to refill a slot published fewer than two blocks ago (the same `retiredAtBlock + 2` rule used for snapshots); add the streamed-refill test.

### A-08 — P1 — The baked MixRack changes coefficients without smoothing, from inside the sample loop

`MixRackChannel::processSample` (`app/Source/MixRack.cpp:360-372`) checks the parameter revision **per sample** and, on any change, calls `configure()` (`:212-269`). That rebuilds every EQ biquad, the compressor constants, the Saturn settings and gains, and applies them as a step. Defaults are `eqOn = true`, `maxOn = true`; a knob drag or automation move therefore produces:

- a mid-block CPU spike (EQ/comp/sat reconfiguration, `std::pow`/`std::exp` per band), and
- a discontinuity in gain/width/frequency — the classic zipper/click.

`docs/RELEASE-GATES.md` Gate 5 explicitly accepts only "zero audio artifacts, clicks, pops, zipper noise on parameter changes". Nothing tests that, and there is no ramp/smoother in the rack.

**Fix:** snapshot parameters once per block, ramp gains/width/mix over a few milliseconds, and move `configure()` out of the per-sample path. Add a parameter-sweep click test.

### A-09 — P1 — Real-time performance is unverified and currently under water on a shared box

`NCBenchRender` (rebuilt against the current v3 sources) on this i5-7200U while another session was building:

| Scenario | Block | ns / block | Audio / wall (`realtime_factor`) |
|---|---:|---:|---:|
| idle | 512 | 8.02 ms | **1.45** |
| timeline (16 tracks, 128 clips) | 256 | 8.26 ms | **0.70** |
| timeline | 512 | 14.71 ms | **0.79** |
| timeline | 64 | 1.98 ms | **0.74** |

`realtime_factor < 1` means slower than real time. The benchmark ran while a parallel build occupied the other core, so the absolute numbers are pessimistic, but the **idle floor is 8 ms at 512 frames with no clips**, and every block size lands around 0.7–0.8. The work log's "0.39–0.45 steady" is not what this binary reports today.

There is **no performance gate in CI**: `NCBenchRender` is measured by hand, and a regression does not fail anything.

**Fix:** re-run on a quiet machine, record a baseline for a frozen commit, add a threshold check (e.g. timeline.512 RT factor ≥ 1.5) to CI or a nightly job, and profile the idle strip path before shipping the v3 defaults.

### A-10 — P1 — More than a dozen advertised features are unreachable in the shipped UI

The React workspace covers the window and the native header is hidden (`MainComponent::pitchOpen = true`, `reactArea()` returns the whole window; the View toggle at `MainComponent.cpp:1333` is itself behind the hidden header). The React File/Edit menus then disable, with the hint "Desktop app EDIT → …", features that the user cannot reach in the desktop app:

- **Markers** — add/next/previous/delete; the engine stores and saves them (`MainComponent.cpp:1869-1872`).
- **AudioSuite** — normalise, reverse, invert polarity, gain; implemented and menu-wired natively (`MainComponent.cpp:1767-1777`).
- **MIDI import/export** — implemented natively (`MainComponent.cpp:1270-1271`).
- **Apply Mix Plan / Ask Mix Assistant** — implemented (`MainComponent.cpp:1572-1663`).
- **Mixdown FLAC / MP3 / LUFS-normalised** — implemented (`MainComponent.cpp:1450-1456`); only WAV is exposed through the bridge.
- **Select All Clips**, **Automix Snapshot**, **Documentation**.

`ui/src/workspace/HeaderBar.tsx:293-340` is the source of the disabled entries. This is the largest user-visible gap between "implemented" and "shippable", and it is cheap to close with routes.

**Fix:** add bridge routes for these (most already exist as functions), or remove the entries and provide a visible way back to the legacy native UI while it remains.

### A-11 — P1 — Dirty tracking and autosave ignore mixing, rack, insert and plugin changes

`MainComponent::markDirty()` (`app/Source/MainComponent.cpp:1109-1121`) treats `arrange.undoDepth()` as the only dirty proxy. Mixer moves, channel/master rack parameters, insert loads, plugin loads, mute/solo and track adds do not touch that depth. Consequences:

- Autosave (`maybeAutosave`) never fires for a mix-only session.
- `hasUnsavedSessionWork()` (`:756-772`) only returns true for clips/automation, so an empty session with a mixed rack can close without a prompt.
- A new session with no project file never autosaves at all, and crash recovery only looks beside a remembered project (`:798-863`).

**Fix:** a session dirty counter incremented by every mutating route (or a host "document changed" signal), and a recovery autosave in `userApplicationDataDirectory` for unsaved sessions.

### A-12 — P1 — The soak does not soak what the gate says it soaks

`app/Source/SoakTests.cpp` sets 8 tracks, starts the transport and renders blocks; it **never instantiates a hosted plug-in**. `scripts/soak.mjs:71` even records "no hosted plugins exercised (synthetic inserts only)". It runs for 1 minute, checks only `recordOverflows() == 0`, and the test is tagged `[.][soak]` so `ctest` never runs it.

Gate 4 in `docs/RELEASE-GATES.md` requires a **30-minute run with third-party instruments and effects** (FabFilter, Serum, Kontakt), zero leaks and zero overflows. None of that has happened, and the harness cannot report per-plugin failures as the packaging plan requires.

**Fix:** load the registry/installed VST3s into slots, run 30 minutes, record RSS/handle counts, and fail on growth; keep the synthetic run as a separate fast test.

## 4. Medium and low findings

### A-13 — P2 — `Studio.tsx` and `eqCurve.ts` are dead code that breaks the lint gate

`ui/src/console-ui/panels/Studio.tsx` (~20 KB, the new 8-band interactive EQ surface) and `eqCurve.ts` are imported by nothing except each other. They are untracked, unreferenced and produce the only five lint errors. Meanwhile the shipped ChannelStripPanel still exposes **4 EQ bands** (`BAND_DEFAULTS`, `ChannelStripPanel.tsx:66`) while `MixRackChannel::numEqBands = 8` (`MixRack.h:54`) and `README.md:33` advertises an "8-band Pro EQ". Bands 5–8 and per-band mid/side are present in the DSP and reachable from Mixology presets, but not from the faceplate.

**Fix:** either wire `EqSurface` (fixing the conditional hooks and the 4→8 band binding) or delete the dead files and correct the README.

### A-14 — P2 — No undo for mixing or routing

`ArrangeView::pushUndo()` (`ArrangeView.cpp:2262-2264`) snapshots `{clips, selectedClip}` only. Fader, pan, send, mute/solo, rack parameters, insert load/reorder/bypass, master A/B, plugin load/remove and track add/remove are not undoable. In a DAW this is a routine user mistake with no recovery except the last save.

**Fix:** extend the undo document (or add a second command stack) to the mix surface; coalesce parameter drags into one entry.

### A-15 — P2 — Rack faceplates: no focus management and no live meters

`ui/src/workspace/RackPanel.tsx:227-239, 472-484` renders a full-screen `role="dialog"` with **no `aria-modal`, no focus trap, no Escape handler and no backdrop close** (only a CLOSE button). Keyboard focus can move behind the overlay. The panels are passed no `meters`/`getFrame` props, so the "live faceplate" shows no level or spectrum. The store is rebuilt on every `channel`/`master` push (`useMemo([channel, onParam])`), which recreates subscriptions at up to 30 Hz while a knob is dragged.

**Fix:** use the existing `StudioDialog` shell (it has Escape) or add focus management; pass meters/spectrum frames; keep one store and call `update()` instead of recreating it.

### A-16 — P2 — MIDI-learn still has an unbounded queue and a lock on the input thread

`app/Source/MidiLearnManager.cpp:251-253` pushes into an unbounded `std::deque` under a `CriticalSection` from the MIDI callback; `takePendingChange` drains it at 30 Hz. A controller in a tight loop while the message thread is blocked grows memory without limit, and the lock introduces priority inversion into the MIDI input path. This is audit finding DAW-19, still open.

**Fix:** a fixed-size ring with a documented drop policy, or a lock-free SPSC queue as used elsewhere.

### A-17 — P2 — Plugin hosting is in-process only; pluginval is not fully exercised

`HostedInsert` catches C++ exceptions and scrubs non-finite output, but an access violation in a third-party VST3 kills the DAW. The plugin scan is out-of-process (good), but playback/editing is not. `pluginval` level 5 passes for both bundled plug-ins (GUI tests skipped); the official VST3 validator is skipped because its path is not configured (`"Skipping vst3 validator as validator path hasn't been set"`). GUI tests on a real display have not been run.

**Fix:** state the in-process risk explicitly in the release notes, add a crash-recovery/autosave path that covers a plugin crash, and run pluginval with the validator and GUI tests in the gate.

### A-18 — P2 — Distribution prerequisites and legal position are unresolved

- The app needs the VC++ 2015–2022 x64 redistributable and the WebView2 Evergreen Runtime; neither is bundled or checked (A-04).
- The binaries are GPL-3.0 because `nc_mixrack` statically links ChordStudio. `LICENSE` and `THIRD-PARTY-NOTICES.md` are correct, but the package contains no **corresponding source** and no written offer of source, only the repository URL in the notices. GPL §6 requires one or the other for every binary distributed.
- A commercial ChordStudio licence remains an owner decision; nothing in the tree resolves it.

**Fix:** decide GPL vs commercial; if GPL, ship the exact source archive (or a written offer) with the installer and link it from the About dialog; if commercial, replace the vendored dependency.

### A-19 — P2 — No crash handler, log file or support surface

`Main.cpp` sets no `juce::SystemStats::setApplicationCrashHandler`, writes no log, and `moreThanOneInstanceAllowed()` returns `true`. The About dialog in `HeaderBar.tsx:572-576` does not show the version. After a user reports a crash there is nothing to inspect except the WER report; two instances can also fight over the same audio device.

**Fix:** add a crash handler writing a minidump/log to `userApplicationDataDirectory`, a rotating log, version/build hash in About, and a single-instance guard for the audio device (or an explicit "second instance = no audio" mode).

### A-20 — P2 — 150 % DPI and keyboard-only operation are still unverified

`docs/UI-REVIEW.md:221-224` records that at 150 % on a 1366×768 panel the logical area is 890×427, below the design minimum, and the header/transport/inspector overlap. The audit did not re-verify this on the React shell. There is no automated keyboard-only or contrast gate. Release plan gate B5 remains open.

**Fix:** verify at 100/125/150/200 % on 1080p and 1440p; add a keyboard-only scripted pass (Tab/Enter/Escape on every dialog, including the rack overlays); fix the density mode or raise the minimum.

### A-21 — P2 — `collab/` is not part of the DAW

`collab/` is a complete Node relay + phone remote with its own README, Dockerfile and CI jobs, but no native or React code references `HostSession`/`GuestSession` or port 8787. It is either a separate product or dead scope in this repository. Its CI cost and its claim to be a DAW feature are both currently unjustified.

**Fix:** move it to its own repository, or integrate it through documented bridge routes and mark the status in the README.

### A-22 — P3 — Documentation drift (beyond the score claim)

- `.planning/ROADMAP.md` (status 2026-11-12) still marks Phase 2/3/5/6 OPEN, says 168/168 and 81/81, and describes recording as blocked; the tree has 195/196 and 114/114.
- `cmake/Packaging.cmake:1-8` says the app "is deliberately not part of this package", while `CPACK_COMPONENTS_ALL` and `app/CMakeLists.txt` now include it.
- `docs/MIXRACK_V3.md:111` says the four `[mock]` tests "can crash"; three of four do, and the take test writes an empty WAV. That is a failure, not an environment note.
- `WebViewBridge.cpp:344` still says "the four user slots only" above a loop over 8 slots.
- `README.md` advertises an 8-band channel-strip EQ; the shipped faceplate has 4.
- `DAW_WORK_LOG.md` records 196/196 and the old digest.

**Fix:** one status document generated from the last green run; delete duplicated claims from the others.

### A-23 — P3 — Build and artifact hygiene

- `git diff --check` reports trailing whitespace in `ui/src/workspace/workspace.css:2791`.
- `vite build` warns that the main chunk is 562,649 B (> 500 kB); no code splitting.
- `build/` holds ~300 stale logs and screenshots; not shipped, but it makes a "clean build" claim hard to verify and contributed to the stale-benchmark confusion in this audit.
- The `ui/src/console-ui` tree is marked "GENERATED from console-ui — edit there, then run `npm run sync`", but **there is no `sync` script and the source package is not in the checkout**. Local edits (new strip shapes, compressor colours) are being made in generated files and cannot be regenerated.
- Version `0.1.0` is hard-coded in `Main.cpp:111` as well as CMake; the About dialog does not display it.
